浏览器发出请求以后，服务器首先收到的是字节。请求方法、路径、请求头和正文，都需要从这些字节里识别出来。沿着一个小型 C++ HTTP 服务器读下去，最先要弄清楚的，就是“收到数据”和“收到完整请求”之间的距离。

## 一次读取，未必是一条请求

TCP 提供字节流，不保留应用层消息的边界。一次 `recv()` 可能只读到半行请求头，也可能同时读到请求头和一部分正文。客户端一次发送了多少字节，不能决定服务器一次能读到多少。

假设请求头声明 `Content-Length: 3`，正文分两次到达：

```text
第一次收到正文：ab
第二次收到正文：c
```

第一次读取后，服务器必须继续等待。只有三个字节全部到齐，才能把这条请求交给业务处理。这里计算的是字节数；正文含中文时，字符数和字节数可能不同。

## 状态机负责记住“读到哪里”

[`HttpRequest.h`](https://github.com/Hokkaidoooo/cpp-http-server/blob/main/HttpRequest.h) 把解析过程分成几个状态：

```text
RequestLine → Headers → Body → Complete
解析错误 → Failed
```

`feed()` 把新字节加入缓冲区，再从上次的位置继续。请求行和请求头以 `\r\n` 分行，头部后的空行标记正文开始。正文不足声明长度时保留状态，恰好到齐才进入 `Complete`。

边界也由这里统一判断：POST 缺少 `Content-Length` 返回 411；重复请求头返回 400；正文超过声明长度会报错。连接提前结束时，解析器不会把半条请求当成成功。

这些限制属于本项目的协议范围，不能直接当作所有 HTTP 服务器的行为。当前实现仅支持 HTTP/1.1 的 GET、POST，不支持 chunked 或流水线请求。

## 完整请求进入队列，连接留在原处

[`HttpServer.h`](https://github.com/Hokkaidoooo/cpp-http-server/blob/main/HttpServer.h) 中，epoll 线程负责连接、读取和发送。解析完成后，请求才进入有界工作队列，由工作线程执行路由及业务逻辑。队列满时返回 503，避免任务无限堆积。

工作线程持有请求值和连接代号，不持有套接字。处理完成后，它把响应放入完成队列，通过 `eventfd` 通知 epoll 线程。

这样分工还有一个容易忽略的作用：操作系统会复用文件描述符。旧请求处理完时，原连接可能已经被回收，同一个描述符也可能属于新客户端。按递增的连接代号查找，才能避免把旧响应发给后来的人；查不到对应连接的结果会被忽略。

## 响应生成以后，还要处理部分写入

一次 `send()` 也可能只接受部分待发送数据。代码保存已发送的偏移量，下一次从剩余位置继续；遇到暂时不可写的 `EAGAIN`，就等待新的可写事件。

[`HttpResponse.h`](https://github.com/Hokkaidoooo/cpp-http-server/blob/main/HttpResponse.h) 统一生成 `Content-Length` 和 `Connection: close`。全部响应字节提交发送后，服务器关闭连接。这是“每个连接处理一个请求”的实现，没有 keep-alive。

继续阅读代码时，可以沿着三个问题往下找：请求什么时候完整，连接由谁持有，响应还剩多少字节。把这三处状态看清，线程池和 epoll 之间的配合就更容易理解。
