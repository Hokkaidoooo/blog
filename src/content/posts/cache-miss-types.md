看到 Cache miss，直觉上很容易想到“缓存太小”。但即使还有空位置，某个数据块也可能因为映射限制而放不进去。要判断原因，需要同时看访问历史、映射方式和替换策略。

下面沿用[系统原理实验室](https://hokkaidoooo.github.io/cs-systems-lab/#cache)的单级只读模型：Cache 初始为空，输入是字节地址。讨论重点是访问轨迹，不涉及真实处理器的访问延迟。

## 先把地址换成块号

Cache 按块保存数据。块号等于地址除以块大小后向下取整；组号等于块号对组数取余。总块数由容量除以块大小得到，再除以路数得到组数。

例如块大小是 16 B，地址 0 和地址 1 都属于块 0。因此，“第一次访问这个块”不能写成“第一次访问这个地址”。已经读过地址 0，再读地址 1，不算首次访问新块。

直接映射每组只能放一块。不同块若算出相同组号，就必须争用同一个位置，其他组空着也帮不上忙。

## 三个标签，需要一个共同参照

实验室针对 LRU 维护一个“影子 Cache”：块大小和总容量与实际 Cache 相同，但采用全相联，不再限制块必须进入哪一组。它同样按 LRU 替换，也接收完整的访问序列。

每次实际 Cache 未命中时，按这个顺序判断：

- 此前从未访问过该块：强制未命中。
- 已经访问过，影子 Cache 也未命中：容量未命中。
- 已经访问过，影子 Cache 能命中：冲突未命中。

影子 Cache 必须连实际命中的访问也一起处理，因为命中会改变 LRU 的先后顺序。若只把 miss 喂给影子，它看到的历史就变了，后续分类也可能出错。实际命中的访问本身不增加任何 3C 计数。

## 用两段序列把差别算出来

先看容量 4 B、块大小 1 B 的直接映射 Cache，共有四组。块 0 和块 4 都映射到组 0：

```text
访问块号：0 → 4 → 0 → 4
未命中：  强制 → 强制 → 冲突 → 冲突
```

前两次是首次访问。第三次再读块 0 时，它已被块 4 挤走；但同容量的全相联影子能够同时保存这两块，所以第三、四次都是冲突未命中。这里增加容量并非唯一改法，改变相联度也能消除这段序列中的冲突。

再看容量 2 B、块大小 1 B、2 路全相联的 Cache，整个缓存只能放两块：

```text
访问块号：0 → 1 → 2 → 0
未命中：  强制 → 强制 → 强制 → 容量
```

前三次都是首次访问。装入块 2 时，LRU 淘汰块 0；第四次再读块 0，影子也已经没有它。去掉组映射限制仍然放不下，因此归为容量未命中。

两例的块大小都是 1 B，块号恰好等于字节地址。若保持块数、换用更大的块，需要同步调整容量，再把块号乘以块大小，得到实验页面接受的字节地址。

## 为什么 FIFO 不照搬这套标签

LRU 在命中时更新最近使用顺序，FIFO 不更新。两者出现不同的 miss，原因可能是替换策略，而非组映射限制。即使 FIFO 已经全相联，也可能比同容量 LRU 多一次未命中。

因此，当前[计算实现](https://github.com/Hokkaidoooo/cs-systems-lab/blob/main/src/models/cache.js)会统计 FIFO 的命中与替换过程，但将 `classification` 设为 `null`。具体口径见[模型说明](https://github.com/Hokkaidoooo/cs-systems-lab/blob/main/docs/models.md#3c-分类口径)。读分类结果时，把参照策略一起读出来，才能知道这个标签究竟说明了什么。
